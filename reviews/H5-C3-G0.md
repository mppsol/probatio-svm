# H5 · C3 G0 review

**Verdict: KILL AT DESIGN GATE — condition A / the founder’s three-meaningful-capital-actions condition is not met.** `W1`/`W2` is 件数合わせ: no concrete operational reason justifies splitting a 200,000,000-atom withdrawal into two 100,000,000-atom calls when the cited fixture admits a single 486,657,686-atom call. Do not measure C3.

I wrote the earlier `DISSENT` that correctly separated C3’s client-fault trigger from its real-BPF cumulative failure. This review is of the consequence of that finding under the now-fixed G0, not a re-review of my H4 implementation.

## P0

- **Artificial tranching makes the third capital action padding.** `docs/H5-C3-G0.md:55-79` calls chunking “ordinary” but supplies no size limit, operational policy, liquidity constraint, timing requirement, or risk rule that requires it. The only demonstrated ceiling is 486,657,686 atoms, well above the proposed 200,000,000 total. The two planned tranches exist solely so one retry yields three actions. This violates the explicit design-time kill at `docs/H5-C3-G0.md:238-242`.

- **`Pol` is too weak to support the claimed distinction from a runtime wallet policy.** `docs/H5-C3-G0.md:172-178` selects only an allowlist and one-call cap, omitting a rolling/cumulative limit or an approved-intent total. Such controls are reasonable for capital-policy products and catch a duplicate ordinary withdrawal. The stipulated narrow `Pol` will miss, but that does not establish H5 condition B against “a runtime wallet policy” (`docs/H5-GATE.md:25-35, 94-100`). A GO would be unearned.

- **Material execution choices remain post-run freedoms.** The slots are merely “recorded by the run,” not fixed (`docs/H5-C3-G0.md:81`); the document permits further mutations if disclosed (`:201-203`); and no input contract for the developer’s agent rule exists despite the claim that it is an input (`:225-226`). Slot progression can affect lending state and W3’s result. These must not be selected after observing a result.

- **The CI entrypoint is not yet concrete for a developer’s own agent.** The shown command accepts only an episode JSON (`docs/H5-C3-G0.md:211-225`), not a rule artifact, interface, or deterministic invocation contract. Thus it does not yet meet the gate’s own-agent requirement (`docs/H5-GATE.md:138-142`) and presently risks KILL-4.

## P1

- **Sequential headroom is unproven.** H4 case E proves a single 486,657,686-atom call from the initial fixture, not that three calls totaling 300,000,000 succeed after prior state changes. `docs/H5-CANDIDATES.md:114-120` already records this path-dependence gap. It is an honest KILL-2 risk, not evidence for the prediction in `docs/H5-C3-G0.md:75-79, 250`.

- **Agent behavior is incomplete outside the intended path.** `docs/H5-C3-G0.md:118-135` has no rule for an `Err`, an unexpected status, or repeated timeout. The specified W2-only injection prevents an infinite loop in the hoped-for trace, but a refused W3 leaves the agent behavior undefined rather than deterministically terminated.

- **The “state-bytes-only” predicate conflicts with P3.** P3 requires knowing each transaction “returned Ok” (`docs/H5-C3-G0.md:142-157`), which is execution-result metadata, not state bytes. Per-transaction state deltas can be byte-derived; result status cannot be established by state bytes alone.

## P2

- The binary and fixture hashes are pinned, and use of `klend_new` only is clear (`docs/H5-C3-G0.md:185-199`). The two inherited mutations are substantially identified, but “any further mutation” should be forbidden rather than merely disclosed.

## Direct answers

1. **No: the three actions are not honestly meaningful.** There is no recorded operational reason to chunk 200,000,000 into two calls. “Ordinary agent behaviour” is assertion, not a constraint. The two-tranche plan is filler to make duplicate retry number three. **C3 dies here.**

2. **The injection is legitimate as specified.** Section 3 confines it to the agent-facing W2 submit/confirm result and expressly prohibits VM, transaction, and account effects (`docs/H5-C3-G0.md:84-96`). Thus the chain is not lied to in the specification. With no implementation, I could not verify enforcement.

3. **The signature guard is sufficient against runtime duplicate-signature deduplication if implemented.** A distinct recent blockhash creates a distinct signed message/signature, so W3 tests a semantic duplicate by the agent, not a signature-cache duplicate. But exact slot/blockhash progression is not frozen, and read-only review cannot establish LiteSVM’s validator-equivalent blockhash/cache behavior.

4. **Not complete.** The intended W2-timeout/W3-Ok path terminates. Other results are unspecified, and W3 refusal can leave no defined transition. The correct comparator is fair for the narrow deterministic timeout path, but its state check needs an exact comparison rule and error behavior.

5. **The predicate identifies excess cumulative movement, but P3 does not prove that no per-transaction check could flag it.** It proves each primitive withdrawal can look normal. A policy with an approved-plan total or cumulative spend state can still flag W3. Further, `P1 ∧ P2 ∧ P3` can describe other ledger/plan errors; it does not, by state bytes alone, prove the lost-confirmation causal story.

6. **The 150,000,000 cap is reverse-engineered to miss.** It is selected after choosing 100,000,000 tranches and excludes exactly the intended total while allowing every call. Under the founder’s narrow §0 definition, neither `Pol` nor non-chaining `Sim` catches C3. But a reasonable wallet policy with a cumulative/intent cap catches it, so this comparator cannot carry the broader condition-B claim.

7. **Several things remain unpinned:** exact slot schedule, blockhash-generation/validity rule, prohibition of additional mutations, agent-rule input interface, and the contents/hash of `fixtures/h5/c3-episode.json`. The binary selection, stated hashes, and two named mutations are otherwise adequately identified.

8. **No.** H4’s case A and case E are single calls from the same initial cloned fixture. They do not establish that the post-W1 and post-W2 solvency envelopes admit another 100,000,000 withdrawal. This is the previously identified path-dependence assumption, expressly unproven in `docs/H5-CANDIDATES.md:114-120`.

9. **C3 does not clear condition 2 as a claim about static/runtime policies.** Section 7 faithfully applies the founder’s narrow non-persistent `Sim` rule and permits full inspection of each returned post-state (`docs/H5-C3-G0.md:170-180`). Such a simulator cannot see cumulative P1/P2 without chaining. That does not cure the inadequate `Pol` comparator.

10. **The one change that most reduces a dishonest GO is to reject the artificial tranche split.** It does not save C3; it correctly leaves only one planned withdrawal plus one duplicate, below the required three actions. **C3 should not be measured.** The design gate is intended to stop this exact kind of count-fitting before implementation.
